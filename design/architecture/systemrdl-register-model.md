# 寄存器模型与 SystemRDL 接入设计

SystemRDL 支持已列入后续工作，当前尚未实现。本文说明寄存器模型在 XReactor 中的位置，以及文件生成与运行时构建的取舍。推荐先采用构建时生成 Python 访问包、运行时绑定总线 Agent 的方式；具体接口和工具版本在实施时确定。

实施范围和验收要求见 [SystemRDL 支持计划](../delivery/systemrdl-support.md)。当前 Agent 与参考模型的使用契约见[用户指南](../../docs/guides/agents-and-reference-models.md)。

## 要解决的问题

寄存器接口通常需要在 RTL、软件头文件、验证代码和说明文档中重复定义地址、字段位宽、访问权限和复位值。人工维护多份定义容易产生差异，例如 RTL 已经移动某个字段，测试仍向旧位置写入。

SystemRDL 用一份规格描述寄存器结构及相关行为，PeakRDL 工具链可以据此生成不同用途的产物。对 XReactor 而言，首要用途是生成 Python 寄存器访问对象，减少测试中手写地址和位操作的代码。该能力主要服务于具有控制和状态寄存器的模块；Cache 数据通路、取指协议等验证仍使用各自的事务模型。[SystemRDL 标准](https://www.accellera.org/downloads/standards/systemrdl)、[PeakRDL 工具链](https://peakrdl.readthedocs.io/en/latest/index.html)

## 寄存器模型与现有组件的关系

这里的“寄存器模型”包含几种不同职责，实施时应分别处理。

| 职责 | 内容 | 建议归属 |
| --- | --- | --- |
| 规格描述 | 地址、层次、字段、权限、复位值和特殊访问行为 | 来自 SystemRDL 的生成物，同一配置可以共享 |
| 访问对象 | 提供具名的寄存器和字段读写，通过回调执行总线事务 | 测试环境创建，绑定具体 Agent |
| 预期状态 | 记录应该读到的值，以及写入、复位和硬件更新的影响 | 独立参考模型，由环境管理 |
| 协议执行 | 驱动引脚、等待接受、接收并关联响应 | 项目中的总线 Driver、Monitor 和 Agent |

寄存器描述属于 DUT 的规格，运行时对象则属于某个 DUT 实例的测试环境。可以在环境上提供 `regs` 入口，但不要求修改 Picker 生成的 DUT 类，也不把寄存器模型定义为一种特殊 Driver。

这些职责可以由普通 Python 对象组合完成。首轮接入优先验证组合方式，不预先增加 RegisterAgent、RegisterDriver 或新的组件基类。每个 DUT 实例分别创建访问对象和预期状态，避免不同测试共享可变镜像。

## 推荐的生成与接入流程

```text
构建阶段
  SystemRDL 文件和配置
      -> 编译、展开参数并检查规格
      -> PeakRDL-Python 生成访问包

运行阶段
  测试环境创建寄存器访问对象
      -> 绑定异步读写回调
      -> 项目总线 Agent
      -> Driver / Monitor
      -> DUT
```

PeakRDL-Python 提供 Python API 来生成访问包，并支持生成使用异步回调的接口。这使生成任务可以直接进入项目构建脚本。它采用复制运行库到生成包的方式减少部署依赖，编译器和模板工具主要在生成阶段使用；实际依赖以选定版本和生成选项为准。[生成 API](https://peakrdl-python.readthedocs.io/en/latest/api.html)、[运行依赖设计](https://peakrdl-python.readthedocs.io/en/latest/design_decisions.html)

生成任务应当能够独立执行，也可以由统一构建入口调用。只生成 Python 访问包时，它与 Picker 导出可以分别进行；同时生成寄存器 RTL 时，应先生成 RTL，再交给 Picker。仿真启动和 Driver 构造不承担 RDL 编译工作。

运行时绑定仍然是动态的。同一个生成类可以连接不同 DUT 实例、总线接口或测试替身，也可以为不同地址映射创建访问对象。提前生成文件不会把访问对象固定到某个 Agent。

读写回调必须遵循项目总线的完成语义。输入被接受并不等于寄存器操作成功：读取需要返回响应数据，写入需要按协议等待完成并检查错误。当前 Driver 的 `send` 侧重输入接受，具体接入应通过项目已有的响应关联路径完成，不能直接把接受事件当作寄存器读写结果。

## 文件生成与运行时构建的取舍

以下比较是针对 XReactor 的工程判断，没有进行两种方案的启动耗时或内存基准测试。

| 方面 | 构建时生成访问代码 | 运行时解析 RDL 并创建通用对象 |
| --- | --- | --- |
| 编辑与调试 | 生成的属性和方法便于补全、跳转与检查 | 新规格可直接加载，动态属性的静态提示需要额外支持 |
| 错误发现 | 规格错误在生成阶段暴露 | 错误在加载阶段暴露，也可增加提前检查 |
| 测试环境 | 编译和生成依赖可以留在构建侧 | 需要携带 RDL 编译器，并固定其版本 |
| 配置变化 | 为不同配置重新生成产物 | 可以按参数现场创建对象 |
| 产物维护 | 需要防止生成文件过期，可能产生较大的代码差异 | 减少生成代码，但仍要维护规格、配置和工具版本 |
| 接入成本 | 可以复用 PeakRDL-Python，重点实现总线回调 | 需要实现编译节点到访问对象的映射和行为支持 |

SystemRDL Compiler 提供编译和参数展开 API，可以在 Python 进程中得到寄存器节点树。因此运行时构建在技术上可行。不过，从节点树到具名访问对象仍需要实现访问层；编译器 API 本身不提供这一层。[编译与参数展开 API](https://systemrdl-compiler.readthedocs.io/en/stable/api/compiler.html)

运行时解析更适合交互式工具、加载事先未知的寄存器表，或者频繁切换规格配置的场景。对于已经编译好的 RTL，Python 侧仍必须使用与该 RTL 一致的配置，不能仅靠重新加载 RDL 改变 DUT 的寄存器布局。

开发阶段可以自动检查规格变化并重新生成文件。这仍属于文件生成流程，却能提供修改后直接运行的体验；无需因此引入常驻编译器或仿真中的规格热更新。

## 元数据方案的适用条件

另一种路线是在构建时导出寄存器元数据，运行时由通用的 RegisterBlock、Register 和 Field 对象加载。这样既能把编译器留在构建侧，也能减少每份规格生成的 Python 类。

这条路线需要我们维护元数据格式和通用访问实现，明确如何保存数组、枚举、权限、复位值和特殊读写语义。简单的地址与字段 JSON 不足以代表完整 SystemRDL。只有当多个工具需要共享寄存器元数据，或生成代码规模形成实际问题时，再评估是否值得承担这部分维护成本。

首轮推荐复用 PeakRDL-Python 输出，不自行编写 RDL 解析器或通用元数据执行器。

## 规格和生成物的一致性

RDL 是寄存器规格的权威来源，生成文件应由工具更新。生成配置需要显式记录输入文件顺序、顶层地址映射、参数、预处理定义和工具版本，便于核对它与 RTL 使用的规格是否一致。

生成物是否提交到仓库由项目选择：可以在 CI 和发布时生成，也可以随代码提交并检查重新生成后的差异。两种方式都需要保证使用的是对应配置的产物。

若增加缓存，缓存身份应包含所有输入及 include 文件的内容、配置、生成选项和工具版本。只检查入口 RDL 文件的时间戳或摘要，无法识别被包含文件的变化。

## 寄存器访问与行为检查

第一阶段的目标是具名访问和总线接入。预期值镜像、由 Monitor 观察总线来更新模型、硬件主动更新寄存器的预测，以及自动寄存器测试，属于后续验证能力。

这些能力应按具体场景逐步加入。普通读写寄存器与写一清零字段的状态更新方式不同，具有硬件更新或读取副作用的寄存器也需要独立规则。生成器的实际支持范围应在接入时核对；参考模型不能直接把 DUT 的读回值当作预期值。
