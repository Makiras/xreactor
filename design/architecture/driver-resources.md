# Driver 资源占用接口分析

状态：2026-09-29，契约细化稿。用户已确认“预先声明、作用域占用、占用者诊断”的
范围，内部继续使用原生锁；跨 Driver 共享与多资源原子申请另行讨论。
本轮只细化契约，不新增资源类或改变锁接口。
发送入口的已实施契约见[Driver 指南](../../docs/guides/drivers.md)。

## Driver 能力边界

| 层次 | 现有职责 | 不应由该层推断的行为 |
| --- | --- | --- |
| Driver | send 返回可等待的驱动完成事件、close | 后台队列、输入接受协议、响应生命周期 |
| SignalDriver | 信号 ownership、方向检查和释放 | 流水阶段及调度策略 |
| SyncDriver | 调用方等待输入接受；max_active 与按名资源锁 | 为每次 send 自动创建后台任务 |
| AsyncDriver | 后台提交、容量、接受/响应句柄、任务清理 | DUT 响应时序与硬件内部流水结构 |
| SingleCycle 模板 | 显式绑定数据、单周期输入与 idle 策略 | 其他协议的接受条件 |
| 项目协议 Driver | 在 Sync/Async 模板上定义信号操作与接受条件 | 自动推断 DUT 的资源与响应规则 |

独立 ReadyValidDriver 已在后续接口收敛中移除。协议 Driver 应按调用方式选择
SyncDriver 或 AsyncDriver，复用其并发和清理；Cache 的项目级 Driver 已改为 SyncDriver
子类。不同协议仍自行定义时序，不因为一类多阶段示例就统一改成排队模型。

## 当前 resource_lock 实际提供什么

SyncDriver 和 AsyncDriver 使用私有 DriveControl。resource_lock(name) 从当前
Driver 的字典中取得同名 asyncio.Lock；同名键复用同一把锁，不同 Driver 各自独立。
具体 Driver 用 async with 表达占用期间，普通测试只发送请求。

底层复用原生锁的理由是它已有挂起、唤醒、等待顺序和取消处理，并能直接参与
Execution 的即时回调收敛。封装领域接口也可以继续使用原生锁；没有必要因此另做
调度器或把时钟推进逻辑搬回 Driver。

当前暴露原生类型存在真实不足：

- 资源名拼错会悄悄创建另一把锁，不能诊断遗漏的互斥。
- 错误没有附带 Driver、输入请求和资源占用者的信息。
- acquire/release 允许脱离词法作用域使用；原生锁本身不验证事务占用者。
- 同名资源不跨 Driver 共享；锁也不会改变或绕过信号 ownership。
- 一把互斥锁只能表示单个占用名额，不能直接表达多入口容量或组合资源申请。

因此可适配的是资源声明、占用范围和诊断；只把 Lock 改名不会解决这些问题。

## 三类限制不能混为一谈

| 当前限制 | 管理对象 | 释放时机 |
| --- | --- | --- |
| capacity | AsyncDriver 尚未结束的提交，包括等待响应的事务 | send 在接受时；submit 在响应完成/失败或取消时 |
| max_active | 正在执行输入驱动过程的请求 | _drive_one 结束时 |
| resource_lock | 具体驱动过程声明的共享资源 | 离开对应 async with 时 |

这些都不是从 RTL 推断的流水级数。三周期延迟的流水模块可能每拍接收一个输入，
不能因为延迟是三周期，就让一把输入锁占用三周期。锁的范围必须对应驱动端实际
占用的信号或资源，而不是把响应延迟当成输入互斥时间。

流水示例在退出第一段占用后才等待第二段资源。此时 request 保存在驱动协程里；
这种等待能力是示例的具体模型，不自动代表 DUT 存在阶段间缓冲。若实际设计要求
保留上游信号直到下游接收，必须由具体 Driver 明确占用和转交规则，不能由通用
资源包装器假定。

## 可考虑的适配方向

建议优先考虑一个由具体组件显式声明的资源占用接口，默认单名额，用作用域管理
持有和释放；内部仍委托 asyncio.Lock/Semaphore。测试作者不操作这些底层原语。

值得提供的能力包括：

1. 预先声明资源，拒绝拼错或未声明的名称。
2. 记录组件、请求标识、占用起点，错误能指出谁在等待谁。
3. 取消或异常时先完成具体驱动清理，再释放占用，沿用组件的任务所有权。
4. 需要周期预算时显式提供 clock 和周期数，不把墙钟 timeout 冒充仿真超时。

这仍是候选能力集，尚未冻结公共命名或实现。现有 resource_lock 用法已能表达简单
阶段互斥，只有额外语义明确后才值得替换其公共返回类型。

以下扩展需要独立用例和契约，不能顺手加入默认锁：

- 多名额资源：名额表示端口数、缓冲项还是事务额度，需要使用者明确。
- 多资源同时申请：简单嵌套可能死锁，需要明确原子申请或统一获取顺序的边界。
- 跨 Driver 共享：需要显式共享资源对象及生命周期，不能依赖全局同名字符串；
  驱动相同信号仍须满足单一 ownership，不能用共享锁偷偷绕过。
- 硬件仲裁：优先级、轮询、特定采样边沿等属于具体设计，通用资源不默认推断。

## 与时钟阶段收敛的关系

Execution 在时钟推进和 DriveStable 采样前，等待当前已经就绪的工作执行完。
释放锁后唤醒的等待者属于这些工作，因此应在当前阶段得到执行机会。
尚未获得资源的任务仍是阻塞任务，不要求时钟等待它完成；否则等待未来时钟事件
才会释放的资源将使仿真死锁。

领域资源接口可以补充占用语义，不能承担或替代这一时钟边界。现有 memory/native
回归已覆盖级联交接、等待者取消、重新申请顺序、异常释放和外部等待；新增包装
若进入实施，应在保持这些检查的基础上再验证它真正增加的资源规则。

## 已确认范围内的具体契约

以下是下一轮实现规格，示意接口尚不存在于当前 Python 包。名称可在实施评审时
统一确定，不为本草稿增加兼容入口。

```python
class ProjectDriver(AsyncDriver):
    def __init__(self, signals, clock):
        self.clock = clock
        super().__init__(
            signals, name="project", max_active=2,
            resources=("input_port", "result_port"),
        )

    async def _drive_one(self, request):
        async with self.use_resource("input_port"):
            try:
                self.write_input(request)
                accepted = await ClockCycles(self.clock, 1)
            finally:
                self.clear_input()
        return accepted
```

声明式能力只进入 SyncDriver/AsyncDriver 共用的私有控制层，不放进 Driver 最小契约，
也不要求所有 SignalDriver 具有提交队列。两种模板提供相同资源规则；SingleCycle 类
保留原时序，不自动拆成流水级。日常测试仍只使用 send/submit。

### 声明与申请

- 每个 Driver 在构造时声明有限的非空字符串名称，拒绝空名、重复声明和非字符串。
- 未声明名称立即失败，错误包含 Driver 名与可用资源；不能悄悄创建锁。
- 默认单名额、Driver 内独占；另一个 Driver 的同名资源完全独立。
- use_resource 返回异步 context manager，不暴露 acquire/release 或底层 Lock。
- 只允许当前 _drive_one 调用申请；在驱动之外、其他 Driver 或已经退出的调用中使用
  立即报错。同一次驱动递归申请同一资源也立即报错，避免自己等待自己。

申请依靠原生 asyncio.Lock 的等待和取消。这里只保证互斥与既有等待顺序，不承诺
硬件仲裁、公平带宽或固定占用周期，不插入额外时钟等待或 sleep(0)。

### 所有者与诊断

所有者是一次输入驱动调用，不是长期存在的 worker task。AsyncDriver 串行 worker
复用时每笔请求仍需独立身份，可关联现有 XTransfer.sequence_id；SyncDriver 为 send
分配局部递增身份，不为诊断虚构响应事务。

提供不可变状态快照，至少包含 Driver 名、资源名、当前调用身份、开始占用的 backend
tick、等待调用身份列表。空闲时 owner/tick 为 None。只保留活跃状态，退出后删除请求
引用，不积累历史，也不自动保存请求 payload。

内部可以用 ContextVar 传递身份，但须验证实际驱动调用和任务归属，不能仅因子任务
继承了 ContextVar 就把它当成同一个占用者。不另建任务工厂或调度器。

### 释放、失败与关闭

| 情况 | 必须发生的结果 |
| --- | --- |
| 正常退出占用块 | 先完成块内 finally，再清空 owner、释放锁、允许既有等待者继续 |
| 等待中被取消 | 删除等待诊断，不改变当前持有者，不消费名额 |
| 持有时异常或取消 | 执行具体 Driver 的 finally，随后释放；原始异常继续传播 |
| 等待唤醒与取消相遇 | 保留 asyncio.Lock 的取消交接规则，不重复释放或遗失后继等待者 |
| Driver 关闭 | 沿用既有任务取消/等待策略，驱动停止后再释放信号 ownership |

不能通过清空状态表强行修复尚未退出的持有者。原始验证异常与独立清理错误都保留。
取消句柄的等待者仍不代表取消底层事务，资源接口不能改变这个约定。

### 明确不在这一步解决

capacity、max_active 与资源占用继续是三个独立限制。资源申请不变成等待 capacity 的
提交接口，不绕过信号 ownership，不自动表达 reset/flush 或阶段间缓冲。

多个不同资源可按项目明确的固定顺序嵌套，每个申请独立；不承诺原子取得全部资源，
不在等待时偷偷释放已持有资源。避免相反获取顺序是项目责任，通用层提供 owner/waiter
诊断，不增加自动死锁恢复。跨 Driver 共享、多名额和多资源原子申请需要独立用例。

时限暂不混入互斥接口：后续若支持周期超时，必须显式 clock 和预算，不能把墙钟
超时冒充硬件周期。普通用例也不需要自己操作底层 asyncio.Lock。

### 下一轮实现验收

1. 声明错误、拼错名字、错误调用域和递归占用立即报错且不改变持有状态。
2. 诊断随请求变化，串行 worker 复用不能把连续请求视作同一 owner。
3. 等待取消、持有取消、异常 finally、Driver 关闭后锁和诊断均无残留。
4. 同名资源跨 Driver 独立，信号 ownership 冲突继续照常报错。
5. Sync/Async 在 memory/native 下保持原接受顺序、并发限制、连续提交时序。
6. 交接继续由 Execution 的即时回调收敛保证，不往 Driver 添加让拍补丁。

这些是公共接口变更的验收要求；本轮 Monitor/pytest/组合配方不依赖这个草案。
